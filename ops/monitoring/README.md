# Production monitoring

Uptime Kuma 2.5.6 runs as the `deploy` user through `ops/quadlet/uptime-kuma.container`, pinned by digest. It retains `uptime-kuma-data`, host networking, port 3002 and the rootless Podman socket. The administration dashboard requires authentication; `/status/public` deliberately exposes only public service results. Never disable Kuma authentication.

Run `bash ops/monitoring/install.sh` after checkout to install the user units. The installer refreshes units without restarting Kuma. Create `/opt/adhocint/shared/monitoring/config.json` from `config.example.json` with mode 0600 and protect its parent directory with mode 0700. Store `GOKAPI_URL` and `GOKAPI_API_KEY` in `probes.env`, also 0600. These paths, state and credentials are excluded from Git. Use a dedicated Gokapi account with no access to other users' uploads and a key limited to viewing, uploading and deleting its own files.

Create private push tokens in Kuma for Database, Object Storage, Image Delivery, File Sharing API, File Transfers and Probe Heartbeat. Keep the existing monitor IDs and public status groups. Connect functional monitors to the existing Discord notification, set resend interval to zero, and keep container and internal HTTP diagnostics private without notifications. Native HTTPS monitors check the homepage company title, the real Gokapi `/login` title, and projects JSON using `ok = true and $type(projects) = "array"`, expected `true`. Use interval 60, retry interval 30, one retry and timeout 10 seconds. Require HTTP 200 and TLS verification.

Push checks implement the failure threshold in the reporter: the first failure schedules a retry after 30 seconds and sends no changed status; the second reports down; success reports recovery. Configure push monitors with zero retries. Database, storage and authenticated API push intervals are 180 seconds. Image and file transfers run every five minutes, so their Kuma deadlines are 420 seconds. The separate runner heartbeat expires after 180 seconds and detects a stalled scheduler. This installation cannot detect a complete VPS/network outage without an external monitor.

The timer starts one sequential runner every 30 seconds. Routine probes run every minute and transfers every five minutes. Requests, container memory and execution time are bounded. PostgreSQL and S3 checks use the application image and credentials independently of the web process. Public HTTPS probes use the Podman host gateway to reach Apache with the public hostname and certificate verification. Public native Kuma checks also test the public endpoint from the VPS.

Initialize the dedicated S3 read canary once with `python3 ops/monitoring/runner.py --seed`, then validate with `--force --dry-run`. Dry run suppresses Kuma reporting but still performs synthetic transfers. Transfers only create and delete `_monitoring/adhocint/write-<uuid>.bin` objects and the dedicated account's `adhoc-monitor-<uuid>.txt` files. Pending identifiers are saved before uploads and retained until cleanup succeeds. Gokapi canaries expire after one day, are password protected and allow two downloads. Do not delete state while cleanup is pending. Image checks only read already public website images.

Inspect `systemctl --user status adhocint-monitoring.timer adhocint-monitoring.service` and `journalctl --user -u adhocint-monitoring.service`. Logs contain generic results, not tokens or connection strings. Run fixture checks using `node --test ops/monitoring/test_probes.cjs` and, on Linux, `cd ops/monitoring && python3 -m unittest -v test_runner.py`. Simulated failures must use isolated state/configuration and disable notifications.

## Kuma upgrade and rollback

Before a future upgrade, retain the current image and container configuration. Stop only Kuma and archive its complete data directory, including SQLite journal files. Restore to a separate volume and rehearse with `--network none` so copied Discord notifications cannot leave the container. Compare monitor IDs, users, notifications, status groups, uptime history and SQLite integrity before production cutover. Start the tested digest against the production volume only after rehearsal passes.

The 2026-10-22 migration artifacts are retained privately under `/opt/adhocint/shared/kuma-upgrade-20261022`, including the original image and cold v1 archives. Keep them and the rollback image for at least 14 days; do not automatically delete them. For rollback, stop Kuma, restore the original cold archive into an empty volume with ownership preserved, and start the retained original image/configuration. Never run v1 against a database migrated by v2. Preserve subsequent monitoring configuration/history before rollback.
